# V0.4 候选规范的双向丢包重试界勘误

状态：待纳入下一版本的规范修订；不改写 Day60 冻结实验，也不宣称整个协商流程已获新界证明。

## 发现

[`RDINP-COMPOSITION-CORE-V0.4.md`](6g-rdinp-v0.4-draft/composition-core/RDINP-COMPOSITION-CORE-V0.4.md) §1、§3、§8.2 使用“相关方向的连续丢包不超过 B”的条件式活性表述，同时规定一次请求–响应的 `A=B+1` 和 `firstResponseGuard=B×R+C`。若该条件允许**请求与响应两个方向同时各有最多 B 个连续丢包**，这两个式子不足以保证收到响应。

最小反例：`B=1, A=2`。第 1 次请求丢失；第 2 次请求到达但对应响应丢失。两个方向均满足各自的连续丢包上界，发起方仍无决定。`B=2, A=3` 也可由前两次请求丢失、第三次请求到达但响应丢失构造。

Day60 的预注册矩阵每个 trial **只选择 REQUEST 或 RESPONSE 一个注入方向**，并在该方向施加一次初始连续丢包；72/72 验证通过支持这一限定场景及其资源语义，不覆盖上述双向同时或反复出现的合法丢包轨迹。因此历史实验数据不需要撤销，但不能用它证明较宽的双向主张。

## 单次请求–响应操作的候选界

设请求方向连续丢包界为 `Bq`，响应方向连续丢包界为 `Br`。每个到达的请求产生一条可关联的响应；每条响应在有限处理/传输预算内生成。若两个方向的丢包界分别作用于实际发送的消息序列，最坏情形下至少需要 `Br+1` 个到达请求，才能保证一条响应到达；要保证这些到达请求，每个可间隔最多 `Bq` 个丢失请求。所以最少的预定请求尝试数是：

```text
Amin = (Bq + 1) × (Br + 1)
```

这是单次逻辑请求–响应操作在上述理想化模型下的必要且充分尝试数。若仅一个方向可能丢包（另一个方向界为 0），它退化为 `B+1`。当 `Bq=Br=2` 时为 9；前 8 次仍有合法失败轨迹。

在 `t0+kR` 绝对发送时刻、每次成功交换的完整响应时间上界为 `C`、本地发送与响应裁决延迟已经纳入 `C` 的前提下，该单次操作的首次保证响应守卫不得早于 `(Amin-1)×R+C`。若这些本地延迟没有纳入 `C`，必须另加可证明的界。此式**不能直接替换** V0.4 的资源 lease、COMMIT、回执重放和总截止时间：每个后续有损交换都须独立建模，并证明资源不悬挂、幂等与终态一致性。

## 版本化修订选择

1. **收窄 V0.4 适用条件**：在 Profile 中显式写入“单方向、一次初始连续丢包”的故障模型，并把 `B+1` 及现有 Day60 证据只用于该模型。不能把它称为一般双向连续丢包保证。
2. **新增双向 Profile**：分别登记 `requestLossBurstBound`、`responseLossBurstBound`、`maxAttempts`、每个逻辑交换的不可变 operation deadline、调度/处理界和传输上限；语义验证器要求尝试数与时间预算满足双向界，重算全链路 lease/terminal deadline，并新增双向故障、资源变化、回执丢失及跨主机测试。

两种 Profile 可以并存，但 `faultModel` 与其可用保证必须在协商前固定并进入 Profile digest、签名、接口响应和证据账本。接收方不得在运行中把第二种降级为第一种。当前不得将 V0.4 的 `A=B+1` 作为双向一般保证写入最终协议。

## 可复算检查

[`check_rdinp_bidirectional_retry_bound.py`](check_rdinp_bidirectional_retry_bound.py) 用有限状态转移枚举所有未成功轨迹；[`test_rdinp_bidirectional_retry_bound.py`](test_rdinp_bidirectional_retry_bound.py) 检查 `Bq,Br∈0..3`、最小反例和边界。它不覆盖真实计时、重排、资源副作用、签名或完整协议活性。

2026-09-26 增补：有限状态函数可从 `0..Bq` 与 `0..Br` 的任意合法当前连续丢包计数启动，并新增对所有此类起始状态的穷举检查，避免测试隐含“每个 operation 开始就重置链路 burst 计数”。该项仍只验证抽象离散模型的尝试次数，不引入计数器重置、重排或计时保证。
