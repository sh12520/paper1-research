## 2. 当前真实能力与实现架构

### 2.1 实际组件

| 层 | 实际实现和定位 | 能力边界 |
|---|---|---|
| 输入与合同 | `contracts.py:13–120`；三个闭合Schema、OpenAPI | 严格整数JSON、摘要绑定、阶段/消息类型/attempt cap检查；算术接纳不认证实际时间界。 |

| 客户端 | `initiator.py:60–206` | 固定四阶段、非退役重试、严格private-upper选择、winner持久化、写前commitPossible、不可变终态及离线恢复。 |
| 权威 | `authority.py:27–177` | 单诚实SQLite逻辑配额权威；RLock和BEGIN IMMEDIATE；决策、效果、回执和事务关联原子保存。FULL/DELETE持久化。 |
| 审计 | `events.py`、`review_saved_run.py` | 双端轨迹、签名/SQL/事件关联、容量前缀与负控制；保存记录一致性检查，不是执行证明或全程序形式验证。 |

真实调用关系：客户端持久状态 → 签名HTTP请求 → responder鉴权 → authority串行事务 → 稳定业务决策/回执 → 签名响应 → 客户端验签、保存效果知识、竞争winner、持久化并发布终态。

四个阶段是 `INTENT_INITIAL → INTENT_REPLAY → COMMIT_INITIAL → COMMIT_REPLAY`。前两次取得同一固定决策并保存处理witness；后两次首次提交、再观察同一回执。拒绝分支在第二个INTENT决策确认后结束。四阶段并不表示四轮可变QoS报价。

### 2.2 必须保留的三条状态轴

| 状态轴 | 当前含义 |
|---|---|
| 权威资源事实 | RESERVED占用暂存配额；CONFIRMED保留已承诺配额；EXPIRED释放暂存；REJECTED不占用。CONFIRMED没有完成释放机制。 |
| 客户端效果知识 | NO_COMMIT_SENT、UNKNOWN、已知COMMITTED或永久NOT_APPLIED；UNKNOWN不是未提交。`commitPossible`在首COMMIT可能发送前持久化。 |
| 政策完成 | `confirmationComplete`是额外阶段是否完成；不能把其失败解释为资源回滚，不能把其成功解释为业务执行或SLA满足。 |

同一negotiationId绑定intent、principal、units；改变units会触发IDENTITY。重放不续租，已有receipt优先稳定返回。容量不变量是事务边界 `0 ≤ U ≤ P`，其中U为RESERVED+CONFIRMED；Q下调后允许U>Q，不能错误要求始终U≤Q。

重试/故障的已有能力：相同attempt须保持原raw/JCS/messageId/nonce；冲突拒绝；旧attempt不因RTO自动退役；迟到响应不重写终态；首个真实回执已纳入后，后续确认失败不降级知识；提交返回歧义报告UNKNOWN，不能假装rollback；同boot时钟回退和不同boot旧实例被防护；新boot使暂存预留过期，保留CONFIRMED。以上受单权威、可信身份、原子且无回滚存储等前提约束。

当前没有：提议/反提议条款版本、效用/硬约束、动态资源向量、在线消解全部UNKNOWN、A2A实际适配、远程部署、物理执行反馈、多权威事务、CONFIRMED释放。

## 3. 技术缺口：按研发风险排序

以下编号RD独立于历史F01–F15，不以新编号覆盖历史严重度。CRITICAL表示当前会破坏一般合同推论或实际时间保证的依据；MAJOR包括能力缺失与研究证据缺口，并不都表示现有安全内核存在反例。

### RD01 — CRITICAL｜N≥K接受域与N=K时间证明不一致

**定位：** `contracts.py:80–100`；冻结`CONDITIONAL-PROOF.md`的T1/T3；独立理论审查§1/§5；D4-CLOSURE §2。

**证据：** 构造器只拒绝N<K，仍用 `H=(K−1)R+C`。已有合法生成流重排反例：q=0、r=1、K=2、N=3、R=1、C=10；回复生成顺序0→2→1，损失流L,D,L，唯一可用回复upper=12，严格cutoff=12，而旧H=11。它在所述流前提内，不能归档为环境超界。原example的N=K不受此反例推翻。

**影响：** 一般时间充分域无效。lease可行性不仅依赖上游H，还在L94继续使用COMMIT第K个发送位置；只改H会留下另一处不一致。消息计数L102已经按实际N计算，不应误改。

**候选处理：** 新独立候选首先强制N=K；或保留N>K并重新证明全流界，例如候选 `H_N=(N−1)R+C`，同时重算所有prefix、COMMIT最迟发送及replay lookup有效性。后者尚未证明/实现，不能直接写成修复完成。接受域收窄影响兼容性，须用户决定。

### RD02 — CRITICAL｜零deadline margin不能推出严格失败发布

**定位：** `contracts.schema.json:$defs.timing.properties.deadlineSafetyMargin`；`contracts.py:104–108`；`initiator.py:128–144`；独立理论审查§4。

**证据：** margin允许0。当有效cutoff=`D−J_fail−V_fail`时，合法F=cutoff且dispatch、publish用满预算，发布可等于D；目标要求严格小于D。成功prefix严格检查不能补上失败支路的等号。

**候选处理：** 在新受限profile拒绝零margin，或逐配置独立验证严格失败不等式。统一目标为 `F+J_fail+V_fail<D`；不能重复把margin加进严格式，制造对正margin的错误否定。正margin只解决该算术等号，不给阻塞存储/调度建立硬界。

### RD03 — CRITICAL｜实际I/C/d/V/tail仍无合格运行域

**定位：** `initiator.py:103–119、128–144、159–193`；`authority.py:91–99、139–147`；`events.py:27–36`；本报告§4及对应原日志。

**证据：** D5已有两次clean初始化超100ms、170个winning C超120ms、6个tail超50ms；本轮还从同一历史日志得到55/67个clean过渡超20ms、1/34个最终发布区间超100ms。实际每条区间的端点与定位均保存，没有用平均数替代上界。

**影响：** N=K和正margin都满足也不等于现场按时。普通线程、Trace文件I/O、SQLite FULL事务没有所需WCET保证。最终persist若长期阻塞，程序不能靠事后状态检查保证准时发布。

**候选处理：** 先补逐段诊断与成本分解，再在隔离候选评估已验证过的同步Trace句柄复用；所有原负结果保留。不降低SQLite持久性来做性能，不把样本max/p99或扩大预算称为硬实时资格。需要硬期限时另定义可担保运行平台及故障域，不能仅改Python条件句。

### RD04 — MAJOR｜故障测试与计数论证尚未覆盖整个通信时序模型

79条first-effect durable-return tail中6条超50ms：3条故意tail_overrun、3条非故意。非故意为B4 clean seed1 68.9360ms、B2 clean seed6 52.6151ms、B2 late_response seed1 68.2422ms；对应durable return仍分别早于lease约9.147/9.488/9.438秒。这些记录不证明过期后提交，也不证明50ms界成立。

**可确认的机制原因：** 实现让签名、同步Trace、线程竞争、SQLite读写/持久化位于预算路径；R=40ms而C声明120ms，未退役attempt能够重叠，加重处理/观察成本。之前Trace句柄复用实验已经证明该实现因素有可优化成本，但B2退化说明不能推出全路径因果改善。

**尚不能确认的根因：** 缺少可分离的SQL锁等待、commit/fsync、签名CPU、线程调度与文件I/O子区间，以及独立背景负载记录。本轮日志分段不能把104.767ms全归给网络，也不能把tail超界全归给fsync。下一轮应先增加可核对的测量与对照；不预设“换数据库就好”或缩短R必然更快。

## 6. R2的最小设计与A2A边界（建议设计，尚未实现）

采用外层 `OPEN → NEGOTIATING → AGREED / DECLINED / STOPPED`，AGREED后再进入内核资源承诺。提议和反提议共用一种OFFER动作，以parentOffer/version标记关系；另有ACCEPT、DECLINE、STOP。不要求为每个动作新建HTTP endpoint。限定最大轮数和不可滑动会话deadline。

最小条款包括目标、硬约束/可让步范围、offerId/版本、父提议、条款摘要、会话ID和双方身份。策略先用确定性有限目录搜索：可行则接受，不可行则给一个可行反提议，不能满足底线则拒绝。这里的“智能体”来自目标约束与自主选择，是否使用LLM不是协议成立前提。

所有OFFER不占资源；只在最终条款确定后请求一次预留。`ACCEPT`不代表预留成功，`RESERVED`不代表QoS已兑现。第一版不逐轮预留、不续租、不增两套commit。若确需预留后再改价，必须另设计旧预留的失效和替换原子性。

agreement摘要与C2的intentId/negotiationId必须有可信、持久的单值映射，并检查agreement期望的principal、units、合同digest。**把摘要写进intentId本身不等于权威已理解/验证全部QoS条款。** 新账本和适配器属于新增信任边界，需明确审批。重复ACCEPT/崩溃重试必须沿用同一内核key，UNKNOWN时不得新建分配。

STOP只终止尚未进入不可逆效果的外层工作；已经COMMITTED不因STOP撤销。现有暂存依靠expiry；新增主动释放或补偿要另批。

**A2A必要性：** 若只是本项目两个本地智能体验证协商机制，A2A不是前置条件；如果要接入现有agent平台或验证跨框架互操作，再做薄适配。官方固定版本v1.0.0提供context/task多轮关联，但SendMessage幂等性是可选的，CancelTask只是尝试取消，不能替代RDINP持久幂等/效果事实。实现前需固定具体版本和binding；当前评估不等于选定升级。[A2A规范§3.1.5、§3.3.1、§3.4](https://a2a-protocol.org/v1.0.0/specification/)

适配成本主要在task/context到内核key的持久映射、重复投递、重连、鉴权和状态翻译测试。RDINP的UNKNOWN应放入显式效果状态/证据工件；不能随意映射为任务已失败或资源未提交。A2A任务完成的业务含义必须单独约定，不能用COMMITTED冒充业务执行完成。

## 7. 最小6G业务模型与论文研究增量

### 7.1 一个可实验场景（建议设计）

建议用“单MEC边缘准入代理—单业务请求代理的有限批次视频感知卸载”。协商推理质量档位、资源包数量与业务完成期限；单权威管理同一逻辑资源池。没有引入跨域多权威或基站物理调度。

外层意图：质量底线q_min、业务期限D_task、输入量S(q)、计算量C(q)。分开管理协商期限D_neg与任务执行期限；不能把现有5秒合同标成URLLC的无线时延。

候选可行性模型：

`T_neg + T_upload(S(q),b) + T_queue + T_compute(C(q),f) + T_down ≤ D_task`，且`q ≥ q_min`。

第一版unit为固定比例资源包`(b0,f0)`，请求m个包，容量 `P=min(floor(B/b0),floor(F/f0))`；所有任务遵守相同比例，以`Σm≤P`做标量准入，可保守保证资源包库存。该模型牺牲独立带宽/CPU配置自由度；不能直接宣称一般联合最优。

若需要独立b/f向量，应由同一权威原子校验整个向量；不能拆成两笔C2当作联合原子承诺。任务完成释放尚未实现，因此先做有限episode/一次批次的准入；独立实验之间的新资源池初始化须明示，不能当作既有CONFIRMED完成释放或长期稳态吞吐。

参数数值、数据集、设备、q→S/C标定、管理消息路径与SLA出处均为 `[AUTHOR: 待补]`。载频、速度、阵列和前传本版不建模；只有明确控制消息经过无线/前传并要做相应主张时，才加入可追溯配置。IMT-2030框架可以说明应用背景，不能替代本项目参数标定或认证。[ITU-R M.2160-0官方记录](https://www.itu.int/rec/R-REC-M.2160-0-202311-I/en)

### 7.3 哪些可能成为研究机制

| 备选问题 | 可证伪主张与指标 | 基线/消融与主要失败风险 |
|---|---|---|
| Deadline-aware协商 | 在相同质量底线与总预算下，用剩余时间可行性筛选offer/轮数，提高按业务期限达成的比例，减少无效协商成本。 | 固定轮数、固定deadline/简单贪心及最近邻方法；去掉可行性筛选。若只是更早拒绝或放低QoS而成功率升高，不构成预期增益。 |
| Lease锚点与预留自适应 | 原start-based guard是保守充分界；研究按真正预留锚点组织剩余成本，减少不必要拒绝/闲置，同时保持条件安全。 | 原保守界、固定lease；分别去掉锚点修正/自适应。新lease须在首次预留前确定，不通过replay续租。需先给无循环条件证明；不能仅用历史最大值选lease。 |
| 效果不确定性感知策略 | 显式区分UNKNOWN与永久结果，在受限恢复条件下减少不必要新分配、悬而未决时长/资源闲置及额外通信。 | 固定重试/固定确认政策；去掉知识策略。不能承诺永久丢失网络下有限时间消除全部UNKNOWN；永久负结果fence是状态合同改动。 |

四阶段的独立贡献应按“intent-replayed witness政策、额外观察与其代价”评估，而非先假定比两阶段安全。GRASP已定义多步目标更新及接受/拒绝，且明确事务完整性需ASA另担；因此新增OFFER/COUNTER或把协商接上事务内核本身不足以证明原创。[RFC8990 §2.8.7–2.8.8、§2.10.4](https://www.rfc-editor.org/rfc/rfc8990.html)

如果以后走R3，建议先聚焦“deadline可行性筛选”一个策略，lease锚点作为受限正确性分析，不同时堆三个算法。是否有独立研究增量，必须先对16篇中的直接近邻及Timed Atomic Commitment进行全文逐主张核验；当前不作首创或投稿档次判断。

共同指标：所有到达意图为分母的准时协议达成率、满足硬QoS底线的效用、拒绝/失败/UNKNOWN比例、publication与任务完成分别计时、消息/字节/SQL事务数、预留闲置`∫units dt`。分布报告n、运行环境和失败数；小n不报有意义的p99承诺。

对照必须固定资源池、意图序列、故障轨迹、搜索/调参预算和持久化强度；B2/B3/B4先满足共同效果合同，再分开政策完成差异。消融一次只动一个机制。逻辑仿真结果只支持所定义模型，不是6G运行资格。

## 8. 推荐下一轮最小开发任务与验收（提案，未下发）

**推荐：R1首批——独立候选中的“受限时间配置接纳与证据检查一致化”。** 先不改四阶段、不增加协商消息、不触碰资源效果及UNKNOWN语义，不启动A2A。它解决的是已成立的错误接受域及盲区，为后续机制实验建立可信入口。

建议边界：新候选显式限定每阶段N=K，采用正deadline margin并独立检查严格失败不等式；保留C2原件与其接受记录。通过单独profile/候选身份绑定规则，不能往C2闭合JSON临时塞字段，也不能仅给客户端加一个可绕过的说明就宣称整个接受域修好了。具体新revision/profile身份随批准后的最小diff明确记录，本文未预先生成。

验收标准：

1. **身份与冻结：** 旧C2/日志/包哈希不变；新候选拥有独立来源身份和精确diff；所有接受域/兼容性变化显式列出。
2. **配置边界：** N<K、N=K、N>K，margin=0/正值，prefix=cutoff−1/等号/+1，均有独立预期。N>K反例作为旧一般主张的负见证保留；新profile拒绝不等于修复了任意N>K证明。
3. **事件边界：** I=预算±1及等号，upper=cutoff±1，publication=D±1，final check+tail+tail margin=lease±1；对应手工/受控时钟见证。实际持久化超界保留COMMITTED和违例，不改成NOT_APPLIED。
4. **不变量：** 旧52方法同版执行并保存全部结果；增量测试独立列数。独立重建U≤P、每key至多一次首效果、永久receipt稳定、重放不续租、首次COMMIT前write-ahead，以及已纳入的真实receipt不因确认失败降级。
5. **通信负例：** 首COMMIT请求全丢、已提交但回执全丢、旧attempt乱序、同attempt冲突/重复、崩溃恢复均分别断言资源事实/知识/完成政策。COMMIT_REPLAY无回执不得被误判NOT_APPLIED。
6. **时间可见性：** 检查器输出I/C/d/V/tail各段，缺端点标“不可判断”，超界不吞掉；不增加预算把旧数据洗成通过。本批不以“比旧版更快”验收，也不宣称硬实时已获认证。
7. **收口：** 交付最小diff、保存回归、残余问题与主张限制；用户可复核。“实现检查完成”“回归通过”“条件证明适用”“实际时间界资格”分栏，不能合并为“协议已证明正确”。

若新边界用例暴露资源效果/消息合同必须变化，应带具体反例和最小替代方案回来，不能扩展首批范围自行修架构。
