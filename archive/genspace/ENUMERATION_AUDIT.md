# Enumeration feasibility audit — PRE-PILOT-CLOSE-01

Status: **blocking; no pilot or smoke authorization follows from this audit**. Only publicly constructed grammar domains and a hand-built legacy unit context were used. No smoke/pilot/confirmation seeds were generated or read.

The proposed full rich domain has 27 B2 profiles (3 quality × 3 deadline × 3 rate values) and one value each for If condition, Sequence duration, Delay offset, ValidFor interval and Offload level. Static depth is 0. For full capability availability, with distinct domain values and ordered children, let `N(0)=27` and `N(d)=27+3*N(d-1)+2*N(d-1)^2`. This counts all typed *syntactic* ASTs, including later semantic/precondition failures: depth 0 = 27, depth 1 = 1,566, depth 2 = 4,909,437, depth 3 = **48,205,158,042,276**. It is an exact count for this public syntactic domain, not a verified-agreement count. Sparse registry counts depend on which operations are available.

An independent bottom-up depth-two reference matches the main generator on both syntactic sets and guarded-schedule-and-cost semantic-key sets for a separate two-profile domain with every constructor, discarding semantically invalid ASTs. A regression test shows that a semantic/dedup key can exist for a candidate rejected at V2; keys must not substitute for capability validation. The key includes registry costs, but broader congruence under nested contexts, every capability combination and all constraints has not been proven. **The exact unique semantic size for the full configured domain remains unavailable**. No unsafe early semantic pruning has been applied; pilot-scale depth-three feasibility remains unresolved.

## Measurements and limits

A reduced 3-profile grammar was used solely for an order-sensitive microbenchmark, not for the exact full-domain count above. A sequential prefix of 10,000 depth-three ASTs took 0.0603 seconds to generate (about 166,000 AST/s). Checking the first 500 with the *legacy* toy validator took 0.0825 seconds (about 6,064 AST/s). These prefixes are highly order-dependent, omit almost all trees and do not measure the current state-machine validator. Naively extrapolating these rates to the full rich syntax count suggests about 9.2 years generation and 252 years validation per instance, respectively, on one core. Such estimates are illustrative rather than reliable runtimes, but show the scale of the problem. No cutoff or private-utility pruning was used.

The mean shallow Python string size for the first 10,000 reduced-domain lossless canonical keys was 211.3 bytes. Applied naively to the full count, this is about 10.2 petabytes of key strings alone, excluding set tables, ASTs, allocator overhead, validation state and output. This is a crude lower-bound-style estimate, not peak memory measurement or a semantic-unique count. Streaming can lower memory but cannot resolve the enumeration cost.

Before smoke, establish a semantics-preserving canonical equivalence with independent depth-two semantic-set tests, benchmark the final validator and full configuration mix, and demonstrate feasibility without private utility pruning. If full enumeration remains impractical, report the blocker; do not silently reduce grammar, depth or candidate set.
