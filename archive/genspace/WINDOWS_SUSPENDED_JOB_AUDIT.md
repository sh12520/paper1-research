# Windows suspended Job engineering audit

The parent-side launcher creates a Job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and verifies that `BREAKAWAY_OK` and `SILENT_BREAKAWAY_OK` are absent. It calls `CreateProcessW` with `CREATE_SUSPENDED`, then `AssignProcessToJobObject` and `IsProcessInJob`, and only then `ResumeThread`. A failed assignment terminates the suspended child. This is execution infrastructure only; it does not modify benchmark semantics.

The current real FAST ENGINEERING audit ([machine-readable evidence](results/windows_lifecycle_finalize_01/report.json)) completed 32/32 pre-existing serialized inputs and found 32/32 exact non-timing matches against their earlier ENGINEERING reference. All eight batches recorded assignment verified, prior suspension, resume count 1, Job limit flags 8192 (kill-on-close alone), expected exit code 0, and zero active Job processes at final accounting. No sampled emergency breach occurred; the minimum observed physical available memory was 3,228,770,304 bytes, and the OS-reported peak worker working set was 696,967,168 bytes. All required event samples and instance transaction validations were present; the source snapshot remained consistent. Job accounting is the authoritative gate for members of the pre-bound, no-breakaway Job; Toolhelp is only diagnostic.

Three short-task probes ([data](results/windows_lifecycle_engineering/lingering_probe.json)) recorded waited, successful children with zero active Job processes as `TERMINATED_OBJECT_QUERYABLE` while their process handles remained open. Their identities were no longer queryable at the first post-close sample; measured disappearance was therefore bounded by sampling resolution, not necessarily instantaneous. Queryability of a terminated kernel object is distinct from process execution.

The new launcher was exercised by a normal real FAST transaction, P4 interrupted commit and recovery, and rejection of a mismatched snapshot ([minimal regression](results/windows_lifecycle_regression/report.json)); all recorded PASS. Previous P1–P5 and other snapshot mismatch evidence remains separate.

**Boundary:** this evidence validates the ENGINEERING-only execution path. `src/engineering_recovery.py` only accepts the ENGINEERING namespace, and `tools/windows_finalize_engineering.py` reads the existing 32 ENGINEERING fixtures. There is no implemented SMOKE-02 192-plan orchestrator integrating this launcher, the SMOKE-02 snapshot, complete/skip and resume, delayed candidate audits, and eight/sixteen repeats. The SMOKE-02 plan and draft preregistration alone are not an executable pipeline. Consequently this report closes the tested Windows launcher engineering slice, not the full pre-SMOKE engineering pipeline. No SMOKE-02, PILOT, or CONFIRM was run and no FROZEN_CONFIG was created.

The current verification run reports 33 passing tests, including the seed-free test that closes the last Job handle while a child and descendant are running and waits for the descendant's process handle to signal termination. The assignment-failure test also checks that the suspended child's Python marker is never created. These tests validate the Job settings and fail-closed launcher behavior under the tested Windows environment.
