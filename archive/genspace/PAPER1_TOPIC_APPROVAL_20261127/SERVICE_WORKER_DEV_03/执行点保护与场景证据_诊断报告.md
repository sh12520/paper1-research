# 旧执行者迟到写入与现有业务证据

2026年11月27日 · 开发诊断

## 1. 受控执行点对照

保留 DEV01 的实际 CPU 图像计算。两个独立进程的结果可写入独立 SQLite 数据库中的业务可见最新输出。父进程用管道控制实验顺序。旧进程 A 已完成计算并保持存活，直到收到发布指令。实际输出字节与参考摘要核对。受控暂停和隔离数据库用于验证机制。

每种条件完整比较三条基线。两个完整运行批次的 6 项结果完全一致。读取各自 SQLite 写入账本独立核对主结果。

| 已有机制 | B 写入后，存活旧进程 A 首次尝试写入 | 同一代授权已过期，尚无新代 |
|---|---|---|
| 幂等键 | 写入成功，最新结果由 B 变成 A | 写入成功 |
| 代际检查与幂等键 | 拒绝，B 保持可见 | 写入成功 |
| 代际检查、执行点截止期与幂等键 | 拒绝，B 保持可见 | 拒绝，没有新增写入 |

在 B 写入后场景，A 的检查发生在 B 提交之后且 A 自己的时间窗尚未结束。由此单独检验旧代际条件。在同代过期场景，没有其他任务代替 A。由此单独检验截止期。当有成功记录时，同操作和内容的重放返回历史结果，写入行数不增加。

三个构件均有先例。Chubby 由接收端检查代际相关的令牌。RIFL 将完成记录和业务写入原子持久化。CoAP 的 If-Match 对资源更新提供现有条件检查。这里采用的是面向同一 SQLite 执行点的同类组合，并未复现完整系统。[Chubby §2.4](https://static.usenix.org/events/osdi06/tech/full_papers/burrows/burrows_html/) · [RIFL](https://web.stanford.edu/~ouster/cgi-bin/papers/rifl.pdf) · [CoAP RFC 7252 §5.10.8.1](https://www.rfc-editor.org/rfc/rfc7252.html#section-5.10.8.1)

## 2. 截止期检查与持久完成

另做四案 SQLite 时间边界实验。正常有 250 ms 余量时，两种守卫均正确写入，观察到的提交返回都在截止前。低余量场景在检查时还剩约 25 ms，并在发起 COMMIT 前注入 80 ms 暂停。仅检查当前时间仍接受，COMMIT 调用开始与返回分别在截止后 58.501 ms 和 61.493 ms。以 80 ms 预留提交尾段余量时，该案拒绝且状态无写入。80 ms 是本实验的工程输入，尚未建立可依赖的系统上界。

这确定了时限指标需要分开。执行点检查的时刻、真实写入可见的时刻与终端观察到回执的时刻各有自己的证据。如果要主张硬性的按期持久效果，则需要独立建立从最终检查到持久化的时间上界及钟差余量。原 RDINP C2 已使用提交尾段和时钟余量守卫。已封存的 092 测试中，该尾段约 74.341 ms，超过声明的 50 ms，但持久提交仍早于原预留期。它提供的是上界假设被破坏的见证。新增低余量对照提供了可观测的晚提交见证。冻结实现未改动。[低余量对照结果](<D:/意图协商论文/论文1/GENSPACE-FAIL-01/PAPER1_TOPIC_APPROVAL_20261127/SERVICE_WORKER_DEV_03/commit_tail_20261127-134428/results.json>) · [冻结 C2 协议](<C:/Users/16043/Documents/Codex/2026-10-24/6g-6g-16-1-intent-based/outputs/rdinp-advisor-final-delivery-20261026-r01/deliverables/RDINP_提交老师_20261026/02_RDINP协议完整版.md>)

## 4. 研究判断

当前 sandbox 的迟到写入由现有强基线完全拦住。已知问题可作为 RDINP 对接实际执行时的验收条件。**本轮没有建立需要新增协商机制的真实业务缺口。** GPU 或更换同机运行环境无法补齐这个证据。重启业务方向所需的第一条证据，是一个现有、可安全隔离运行的执行动作，允许独立读回，并能取得请求、授权失效、实际效果和应用截止的时间记录。只有存在使用原生版本、幂等、时限检查后仍出现的可复现损失，才继续机制研究。
