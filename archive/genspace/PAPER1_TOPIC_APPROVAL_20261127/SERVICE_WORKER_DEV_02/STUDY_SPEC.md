# 顺序任务与持久执行许可开发实验

## 目的

在上轮单任务对照的基础上，验证边缘进程持续运行时，首任务错过确认或回退之后，顺序到达的次任务能否用到已经空闲的执行槽位。需要分别观察冻结 C2 的逻辑配额、应用层可兑现的 worker 许可和实际 CPU 执行。旧 C2 源文件保持原字节。

## 固定对照

- C2 继续用原四阶段控制逻辑与容量为 1 的 SQLite 逻辑账本。业务层使用同任务认证状态查询访问执行许可。许可只在权威已经处理持久 COMMIT 后产生。原账本的 `CONFIRMED` 当真实事实保留。
- 直接幂等对照以任务 ID 通过同一个认证接口和值为 1 的应用执行槽位取得持久许可。查询、过期检查、激活、输入摘要、应用任务、回退在两种路径共享。该基线没有复现 C2 的全部多阶段确认属性。
- 三对输入按固定轮换顺序使用三张本机已有样图。每对任务串行释放。应用截止 800 ms，远端结果等待到 550 ms，次任务在首任务释放后的 900 ms 到达，沿用上轮两档输出。只在不中断同一个边缘进程和两个账本的前提下运行一对。两方法顺序在配置间交替。
- 两种工况为无故障与首任务确认回执及其许可查询在回退前持续丢失。故障后次任务的控制与数据正常。采用应用层故障钩子，非无线实测。
- 另做持久状态重启核验，以及跨请求内容/路由/请求响应的认证负对照、迟到激活和重复请求对照。它们不混入主计数。回退启动与发布以本地单调时钟计，CPU 计算真实发生。共享的是应用管理的执行槽；OS 级 CPU 时间预算并未建立。

## 判定

先报告两任务分别的边缘交付、按期回退、未交付和输出摘要。再检查首任务槽位释放到次任务准入的顺序、首任务提交事实是否保留、次数和资源阻塞层。在无故障也出现永久逻辑配额占位时，失联不应被解释为唯一原因。若普通可过期执行许可已经使次任务能够运行，结论限于已验证的生命周期修复路径，没有新的协商算法证据。
