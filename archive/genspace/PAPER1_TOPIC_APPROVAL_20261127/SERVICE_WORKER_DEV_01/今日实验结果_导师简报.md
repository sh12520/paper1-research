# RDINP 业务执行首轮结果

2026年11月27日 · 开发实验 · Windows 本机 HTTP 回环

## 结论

**工程可行。** 冻结 RDINP 可以接入实际 CPU 任务，在掉回执时按本地任务截止期完成回退。常规的同任务状态查询在权威可达时恢复了边缘结果。查询也不可用时，三种方法都依赖本地回退。现有证据未支持在这个故障场景上继续发明新的协商决策算法。

## 实验设置

用 Pillow 对三张已有样图实际运行灰度转换、模糊、边缘检测和 PNG 编码。边缘档输出 512×512，本地回退档输出 256×256。两档分别与独立预生成的输出摘要核对。分辨率只表示设定的两档工作量和输出模式，感知准确率尚未测量。

冻结的 C2 控制面使用签名、HTTP 和 SQLite。独立的共享应用执行适配器实施有时效的单槽位许可。状态查询读取任务特定的同一执行许可。幂等租约基线使用环回令牌及内存状态，没有实施 C2 的等价签名、持久化和崩溃恢复，因此本报告不从时延差推导协议性能排名。

共 4 个故障条件、3 个输入、3 个方法，形成 36 个同输入配对运行。任务截止 800 ms，距任务释放 550 ms 时停止等待边缘结果并启动本地回退。全程用真实单调时钟。本轮故障为应用层定向抑制。无线故障发生率和实际 6G 链路尚未测量。[预先固定的实验规则](<D:/意图协商论文/论文1/GENSPACE-FAIL-01/PAPER1_TOPIC_APPROVAL_20261127/SERVICE_WORKER_DEV_01/STUDY_SPEC.md>)

## 配对结果

表中是每项 3 个输入的“边缘按期结果数 / 本地按期回退数”。

| 条件 | C2 原确认 | C2 加同任务状态查询 | 幂等租约加查询 |
|---|---:|---:|---:|
| 正常 | 3 / 0 | 3 / 0 | 3 / 0 |
| 首份提交或授权回执丢失 | 3 / 0 | 3 / 0 | 3 / 0 |
| 持续丢失提交或授权回执，状态可查 | 0 / 3 | 3 / 0 | 3 / 0 |
| 持续丢失回执，状态也不可查 | 0 / 3 | 0 / 3 | 0 / 3 |

- **36/36 按期交付且输出摘要匹配。** 24 次采用实际边缘结果，12 次采用实际本地回退。每个任务只发布一次结果。24 次边缘计算的处理时长中位数 31.630 ms，范围 19.740–81.043 ms。12 次本地回退处理时长中位数 17.947 ms，范围 9.390–36.202 ms。这些是开发样本测量值。
- **回执持续丢失、状态可查时**，原 C2 适配器 3 次均回退，平均持有未使用的应用执行槽位 390.572 ms。加入状态查询后 3 次都获得边缘结果，未使用槽位的次数为 0。这个时长是执行许可能力占用，实验未量出 CPU 时间浪费或生产任务被阻塞的概率。
- **过期拒绝、错误令牌拒绝、重复请求仅一次计算**三个负对照全部通过。12 个未使用许可均观察到释放日志，释放事件最晚在许可截止后 16.854 ms 被记录。首次执行资格仍以截止时间处的单调时钟判定。普通主机上的清理回调统计不能充当硬实时释放上界。

## 下一轮需要验证的工作

继续以“服务履约保障”作为选题。下一步把同任务权威查询做成具备认证、持久化和恢复语义的接口，在两个进程或两个端点测量故障恢复与合法释放。用持久运行的单 worker 和顺序到达的第二任务，实测释放后是否能及时再准入。先用同保障的常规基线做对照。

若普通权威查询、执行租约和按期本地回退已经覆盖观测故障，形成协议规范、条件保证和工程验证的贡献。只有实测业务仍存在可复现的剩余失败时，再确定新机制。单主机、同一单调时钟的结论不能推广到两端时钟误差和任意无线失联。
