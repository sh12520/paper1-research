# DG-PCE development prototype specification

Status: fixed development design, not a confirmation method, not a claim of general algorithmic superiority. The design was specified before the development outcome; no benchmark parameter or distribution is changed. The development set consists only of the existing 1,920 serialized PILOT instances. Results and any development gate are exploratory, not confirmation evidence.

## Runtime information boundary

The public search module receives an immutable `PublicView` containing only horizon, states, time/state/resource capacities, scalar profiles, capability availability, registry costs, resource parameters, public hard-constraint descriptors, and allowed composition depth. It does not receive family, pressure or conflict labels, an instance/private hash, the other agent's private preferences or reservation, an oracle outcome or witness, or an attribution result. The protocol grants each agent only its own preferences; between agents it transmits only candidate IDs and ACCEPT/REJECT responses. The offline development harness may read family/oracle/attribution records **after** all methods finish for the instance; those are evaluation labels, never search inputs.

## Public deadlock signature

For each of 27 B2 static profiles, compute its approximate RAN/FH/EDGE load using public profile and resource parameters, excluding capability surcharge. For each cell and resource compute `max(demand-capacity,0)/max(capacity,eps)`, `eps=1e-9`. Pick the profile with the lowest mean across cells/resources. Its deficit array provides per-resource means, per-state means and range, per-time means and range. Early/late relief is `(mean_late_capacity-mean_early_capacity)/max(abs(mean_early_capacity),eps)` per resource. EDGE headroom is `max(mean_EDGE_capacity - min_B2_quality*offload_edge_factor,0)/max(mean_EDGE_capacity,eps)`, reported alongside RAN/FH deficit. The signature includes actual B2 public-feasible candidate count from charged public verification and the capability availability set. These are public heuristic features; omitted capability surcharge and hard constraints mean they are not a V1–V4 verification or a private-acceptance test.

## Probes and ordering

All available depth-one semantic classes using exactly one of C, D, P, O are scored with the same approximate per-cell deficit. P is available if Sequence **or** ValidFor is available. Per group, `raw_relief = best_B2_proxy_violation - best_group_probe_proxy_violation`; the mechanism ranking subtracts `0.02 * best_probe_public_capability_cost + 0.01` structural penalty. Every evaluated singleton proxy and every best-probe vector recomputation is counted as a public probe; the 27 B2 proxy computations are counted separately in setup. No public probe or public ranking computation is silently called an exact verification.

For mechanisms a and b, form per-cell/resource `r_m=max(B2_deficit-probe_m_deficit,0)`. Their public complementarity is `mean(max(r_a,r_b))-max(mean(r_a),mean(r_b))`. Pair priority is `adjusted_relief_a+adjusted_relief_b+complementarity`, descending. This rewards relief in different cells/resources and uses no family, result or preference label.

Within a stage, public candidate ordering minimizes `proxy_violation - 0.025*proxy_margin + 0.02*public_capability_cost + 0.08*(1-public_mean_quality) + 0.01*mechanism_group_count`. Proxy margin is the mean clipped relative capacity surplus; cost is mean active-cell registry execution and resource-surcharge cost. These are ranking scores, not feasibility judgments. Ties use stable class ID. Class membership comes from the frozen semantic graph and current public capability/depth mask, never from oracle success or a selected representative. Structural candidates are limited to at most two distinct mechanism groups in this development version; this restriction is an engineering choice based on prior attribution, not a general necessity theorem. Singleton-only forbids pairs. All comparable structural methods share the same <=2-group space.

## Progressive protocol and budget

Stage 0 exhaustively evaluates the 27 B2 classes and runs the fixed bilateral protocol. Agreement stops structural expansion. Otherwise DG-PCE probes and orders available singleton groups, then searches ordered pairs. The fixed development caps are 128 exact verified candidates per singleton stage and 1,600 per pair stage, with chunks of 16 before each negotiation pass; these caps allow pair exploration within budget. The verifier charges one call for every exact candidate, including all 27 B2 calls and failed public checks. Budgets are 100/500/1,000/5,000/10,000 and represent nested checkpoints of the same deterministic run. The protocol alternates proposals from each agent's own acceptable, locally highest-utility unproposed candidates; the responder returns ACCEPT or REJECT, and its next turn may provide a counterproposal. The fixed maximum is 10,000 proposals. It is a standard development protocol, not claimed as a novel bargaining algorithm.

Across incremental batches, the next proposal attempt starts with the opposite party from the actual last proposer. A party with no acceptable counter does not leak additional private information; the rejection remains the only response. This rule handles consecutive proposals by the same party when its counterpart has no available counter, and does not infer turns from the parity of proposal count. The proposal-round limit is global across batches and stages.

Search reduction is only a reduction in the **number of exact verification calls** relative to full-oracle generated semantic class count. Public setup, number of scored classes, public probe count, probe time, ranking time, proposal counts and end-to-end wall time are reported separately; a reduced exact-call count is not a guarantee of reduced total computation.

The implementation processes only the already-selected, budget-eligible batch of at most 16 semantic classes. For each such class it makes one actual `PublicVerifier.verify(class_id)` API call and charges one budget unit. An exact packed public V1–V4 check is performed for that selected batch; public-pass evidence is reconstructed from the audited six-cell signature, and a normalized witness is materialized only for an agreement. After online methods finish, the trusted harness separately invokes the original `verify_instance` with the real instance to check each distinct agreement and both private acceptances; those offline calls are recorded separately and never influence online ranking or negotiation. `batch_calls`, `batch_candidate_checks` and online `state_machine_calls` are separately recorded; public heuristic scoring of unselected classes is not reported as exact verification. The selected-class packed check was independently compared with the original interpreter on 48 existing PILOT fixtures and 924 legal candidates plus three public capacity boundaries; this evidence does not claim exhaustive validation of arbitrary invalid V1–V3 inputs. A private incrementally maintained heap preserves the original local utility/class-ID tie order and exposes no utility values. Singleton/pair quotas are explicit search limits and hitting a quota does not mean that stage was exhaustively searched.

## Baselines

B2-only uses Stage 0. RANDOM-BUDGET randomly permutes the common legal <=2-group class universe; its deterministic random stream is derived from the sanitized public view, not an instance ID, private hash, family or private preference. FLAT-FEASIBILITY applies the public proxy globally without group staging. GLOBAL-FREQUENCY uses the prior order O, P, C, D solely for this baseline, corresponding to the existing 842-case representative label counts 823, 38, 22, 1 (labels overlap). SINGLETON-ONLY uses DG-PCE's public mechanism ranking but excludes pairs. These baselines do not pay for group probes they do not use. FULL-O1 is the unchanged unlimited diagnostic oracle and is never read by the online methods; its historical output is used offline only for evaluation.
