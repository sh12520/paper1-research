# 四阶段控制面的时间预算复核

首轮开发仿真用两次请求与响应抽象意图和提交。现有 C2 的完整确认路径含四次，依次为初始意图、意图重放、初始提交和提交重放。该差别直接影响紧截止期下还剩多少时间执行任务。[C2 实现规范](../../protocol/c2/CONTRACT.md#c2-four-phases-and-authority)

## 已有记录中的消息和耗时

读取已封存 G1-A 归档，先核对 SHA-256，再匹配中继的请求和应答摘要与终端采用的四阶段应答。读取 36 组无注入故障的旧 B1 运行及其 432 个客户端记录。138 个协商产生完整确认，且四阶段采用的均为编号 0 的应答。230 个记录未产生完整确认，64 个完整确认有至少一个阶段采用后续尝试。以下字节是 138 个已匹配协商的应用层 JSON 消息体，未计 HTTP 头、额外尝试及未来多档条款。

| 阶段 | 发送字节 | 应答字节 |
| --- | ---: | ---: |
| 初始意图 | 999 | 1,356 |
| 意图重放 | 998 | 1,355 |
| 初始提交 | 1,095 | 1,419 |
| 提交重放 | 1,094 | 1,418 |
| 合计 | 4,186 | 5,548 |

共 9,734 字节。Step 1 r02 的结构化成功链路按两次抽象往返合计 1,904 字节。历史 138 个记录从开始协商至发布确认中位数为 2.73 秒，p95 为 3.65 秒。12 个在 345 ms 内发布。这是历史同机夹具的控制耗时分布，不能当作空口时延，也不能当作新原型的已测性能。[原始归档摘要](../durable-worker/evidence/g1a-20261128/g1a-evidence-v1.tar.gz.sha256) · [本次提取与计算](evidence/step1-c2-control-budget.json)

## 400 ms 档下的时间余量

沿用 Step 1 r02 的数据档位、分帧、传输速率及 55 ms 本地预留。计算四次控制往返与任务完成时间，从边缘采用窗口 345 ms 中扣除。每个阶段仍按仿真的 1 ms 处理成本，只使用历史消息大小，不把历史软件耗时混入理想链路计算。固定速率，无排队、抖动、丢包和重传。单元格为三张校准图的剩余时间中位数，括号内为严格早于 345 ms 的张数。

| 空口速率条件 | 控制阶段 | 直接主档 | 上传前选轻量档 | 主档上传后再切轻量档 |
| --- | ---: | ---: | ---: | ---: |
| 正常 | 38.7 ms | +28.2 ms（3/3） | +140.9 ms（3/3） | +107.3 ms（3/3） |
| 持续下降 50% | 41.4 ms | −88.8 ms（0/3） | +74.8 ms（3/3） | +9.1 ms（2/3） |
| 持续下降 75% | 46.8 ms | −323.0 ms（0/3） | −57.4 ms（0/3） | −187.7 ms（0/3） |

同样的理想链路假设下，四阶段相对原两阶段消耗额外 20.1–26.5 ms。持续下降 50% 时，上传前切轻量留出的余量明显大于上传后切换。75% 条件仅指该速率持续覆盖整个任务的情形，原轨迹中恢复后的任务须单列。

该结果为协议原型提供了两个可直接核对的量。首先测现有软件在新任务条件下的**完整四阶段签名确认时延**，再分开测两种切档位置。四阶段的字节开销可装入理想 50% 跌幅的轻量路径，但旧夹具的控制耗时无法支撑直接沿用同样的 400 ms 任务预算。实际结果需以原型日志核对。Step 1 仍保留原 810 对的统计范围，协议改动仍待作者确认。

## 复算

同一个封存归档须在本机或通过参数提供。脚本流式读取压缩包，只写汇总记录。

~~~bash
python -B rdinp/experiments/structured-fast-slow/control_budget.py \
  --archive /path/to/g1a-evidence-v1.tar.gz \
  --out /path/to/new-control-budget.json
~~~
