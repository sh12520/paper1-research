# 实际反向代理路由写入与原生基线对照

2026年11月27日 · 开发诊断

## 研究问题与最小对象

此前的 SQLite 试验说明，真正处理副作用的接口需要自己的授权与时限检查。本轮改用 Caddy 官方 Windows 发行版作为执行端。管理面改变实际反向代理的 upstream，业务面用单独的 HTTP 请求读回真正返回结果的后端。三套后端只服务本地受控样图，返回 Pillow 实际处理的结果。测试范围为 Windows 回环的实际软件路由。实验时限为人为注入的诊断约束。现场无线、实际业务 SLA、真实失效发生率均需另取证据。

## 对照与证据

- 首先验证正常匹配版本的变更以及新连接上的业务读回。
- 比较旧写者读取版本后、由新写者先改变路由时，未携带原生条件的写入和携带原生 `If-Match` 的写入。记录状态码、实际后端及返回体摘要。
- 验证在配置内容不变且请求持有当前 ETag 时，工程授权过期是否改变 Caddy 的原生接受结果。故障调度明确记录在本地时间线。
- 验证配置先改变再恢复到字节相同的有关作用域时，旧 ETag 是否仍能用于更改。若 ETag 重新成立，再对照使用原生元数据保存且不重用的版本标识，前提是 Caddy 允许在同一条件检查作用域中更新该信息。
- 如果原生版本无法拒绝已经过期的同版本请求，再做接收侧简单时间检查的诊断对照，复用相同的 Caddy 配置变更接口。只验证已经过期的请求未被提交给代理，与执行完成前仍需安全时间余量的结论分开。

不使用全局或生产配置。只启动本次管理的独立进程，所有控制和数据连接都在 `127.0.0.1`。数据面测量是 HTTP 后端实际响应到达的观测值。单次管理请求和业务读回之间不是一个事务，需要保留各自时间。测试最多证明受控场景和当前发行版的行为。

## 决策原则

旧命令在原生基线下被拒绝，即把版本冲突列为已有功能。若剩余问题可被带代际的版本标识或接收端期限守卫排除，则将其保留为执行接口约束与验收测试。只有以相同能力条件、时限和故障测得常规方法仍有业务损失，才考虑新增算法。
